DS DJ Booths

Server-synced DJ booth system with positional 3D audio, a professional music player UI, song history, and full target integration — by DS Customs

v1.0.0 QBCore xsound ds_target / qb-target Lua 5.4 Escrow

1 — Overview

DS DJ Booths lets you place any number of DJ booths around your map. Each booth streams audio at a 3D world position via xsound, so volume fades naturally as players move away. Playback state is authoritative on the server — every connected player hears the same track, and late joiners are automatically synced.

Features

3 interaction modesds_target, qb-target, or a custom NUI proximity prompt.
Server-synced playbackPlay, pause, resume, volume, and stop all broadcast to every player in real time.

2 — Requirements

ResourceNotes
qb-coreRequired framework. Must start before ds_djbooths.
xsoundRequired for all audio playback. Must start before ds_djbooths.
ds_target or qb-targetRequired only when Config.TargetSystem is set to one of these. Not needed in "prompt" mode.
DS DJ Booths has no SQL dependency. All playback state and song history lives in server memory and resets on server restart.

3 — Installation

Drop-in

Copy the ds_djbooths folder into your resources directory. No SQL files to run.

server.cfg Start Order

ensure qb-core
ensure xsound
ensure ds_target        # or qb-target — only needed for target mode
ensure ds_djbooths
In "prompt" mode neither ds_target nor qb-target needs to be running.

4 — Configuration — config.lua

All settings live in config.lua, which is fully open and unencrypted.

Global Settings

KeyDefaultDescription
Config.TargetSystem"ds_target"Interaction system to use. Options: "ds_target", "qb-target", "prompt".
Config.PromptKey38Control key used in "prompt" mode. 38 = E key.
Config.PromptDistance2.5Metres from booth coords at which the prompt appears.

Booth Entry Schema

Config.Booths = {
    [1] = {
        -- Display name shown in the target menu or the E prompt
        label      = 'My DJ Booth',

        -- Position of the interaction zone (where players open the UI)
        coords     = vector3(0.0, 0.0, 0.0),

        -- (Optional) Where the sound originates in 3D space.
        -- Omit to use coords above.
        soundCoords = vector3(0.0, 0.0, 0.0),

        -- Volume at the sound origin (0.0 – 1.0)
        volume     = 0.8,

        -- Distance in metres at which the sound becomes inaudible
        distance   = 40.0,

        -- Radius of the interaction zone used by the target / prompt system
        zoneRadius = 2.0,

        -- Whether the track loops automatically when it ends
        loop       = true,

        -- (Optional) Restrict access to one or more job names.
        -- Omit or set to nil to allow everyone.
        jobs       = { 'dj', 'club_owner' },
    },
}

Booth Field Reference

FieldTypeRequiredDescription
labelstringYesName shown in the target option or E prompt HUD element.
coordsvector3YesCentre of the interaction zone. Also used as the map/target position.
soundCoordsvector3NoWorld position the sound radiates from. Falls back to coords when omitted.
volumenumberYesBase volume at the sound origin. Range 0.0–1.0.
distancenumberYesMetres from soundCoords at which the sound becomes fully silent.
zoneRadiusnumberYesRadius of the circle zone / prompt detection sphere in metres.
loopbooleanYesWhen true the track restarts automatically when it ends.
jobstableNoArray of job name strings. If provided, only players on a listed job can interact with the booth.
You can mix restricted and unrestricted booths freely. Booth [1] can be job-locked while booth [2] is open to everyone.

5 — Interaction Modes

Set Config.TargetSystem to one of the three modes below. The value applies globally — all booths use the same system.

ModeDependencyBehaviour
"ds_target"ds_targetRegisters a AddCircleZone for every booth. The option appears in the DS Target radial menu when the player aims at the zone. Job restrictions are enforced natively by ds_target — the option is invisible to unauthorised players.
"qb-target"qb-targetSame as above using qb-target's identical API.
"prompt"NoneA custom NUI prompt appears at the bottom-centre of the screen when the player walks within Config.PromptDistance metres. Press Config.PromptKey (default E) to open the UI. The prompt is never shown to players who lack the required job.
Switching modes only requires changing Config.TargetSystem and restarting the resource. No other code changes are needed.

6 — Job Restrictions

Add a jobs table to any booth entry to restrict who can open the DJ UI at that booth. Leave it out entirely to allow all players.

-- Restricted — only "dj" or "manager" can open this booth
jobs = { 'dj', 'manager' },

-- Unrestricted — no jobs field (or set to nil)

The check reads QBCore.PlayerData.job.name from a local cache that is updated live whenever a player changes job in-game via QBCore:Client:OnPlayerUpdated. There is no need for the player to rejoin or reconnect after a job change.

Target Mode Behaviour

When using ds_target or qb-target, the job restriction is passed natively to the target resource as a grade-hash table ({ jobname = 0 }). The option is completely hidden from the target UI for players who do not hold the required job — it does not appear greyed out, it simply does not exist for them.

Prompt Mode Behaviour

In "prompt" mode the bottom-centre HUD prompt is suppressed entirely for unauthorised players. They receive no visual indication that a DJ booth exists at that location.

7 — The Music Player UI

The NUI opens as a floating dark-glass card. It does not obscure the game world — the background is fully transparent so players can still see and react to their surroundings while the UI is open.

Player Tab

ElementDescription
Disc iconSpins while a track is playing. Stops on pause or idle.
Status badgeShows PLAYING (green), PAUSED (purple), LOADING… (yellow), or OFFLINE (grey).
Live timerCounts up from 0:00 from when the current track started. Hidden when not playing.
Animated equaliser20-bar visualiser with unique timings. Pulses while playing, dims when idle.
Now Playing barShows the current URL with a seamless scrolling marquee. Displays a loading shimmer effect while buffering.
URL inputPaste any YouTube URL or direct audio link. Press Enter or the arrow button to load.
Transport controlsStop, Play/Pause, and Restart (replay from beginning).
Volume sliderGradient fill bar. Changes are broadcast to all players in real time.
Mute buttonLocally mutes/unmutes. Remembers previous volume level.

History Tab

The History tab shows the last 30 tracks played at this booth, most recent first. Each row displays:

  • A YouTube or audio file icon
  • Cleaned display URL (e.g. youtube.com/watch?v=xxxxxxxxxxx)
  • Relative time (e.g. 2m ago, 1h ago)
  • A ▶ play-again button that re-queues the track and switches back to the Player tab

The currently playing track is highlighted with a purple tint in the history list. History persists across stops — stopping a booth does not clear its history.

Closing the UI

The UI can be closed with the ✕ button in the top-right corner, or by pressing ESC. Either method immediately releases mouse focus and returns full game control to the player.

8 — Server-Side Song History

Each booth maintains a rolling history of up to 30 tracks in server memory. The history is stored as an array of { url, playedAt } objects, with the most recent entry at index 1.

Rules

RuleDetail
Max entries30 per booth. The oldest entry is removed automatically when the cap is exceeded.
DeduplicationPlaying the same URL consecutively only creates one history entry.
Survives stopCalling Stop on a booth clears the active playback state but keeps the history intact.
Server restartHistory lives in memory only. It resets when the resource or server restarts.
SyncHistory is sent to all clients when a new track is played, and to each new player on join via the late-joiner sync.
History is per-booth, not per-server. Booths do not share a history list.

9 — Sync & Networking

All playback control flows through the server. The client never directly manipulates another player's audio — it asks the server, the server updates its authoritative state, and then broadcasts to all clients.

Net Event Flow

-- Player queues a track:
Client → TriggerServerEvent("ds_djbooths:server:play", boothId, url, volume)
Server → TriggerClientEvent("ds_djbooths:client:play", -1, boothId, url, volume)
Server → TriggerClientEvent("ds_djbooths:client:history", -1, boothId, history)

-- Player pauses:
Client → TriggerServerEvent("ds_djbooths:server:pause", boothId, timestamp)
Server → TriggerClientEvent("ds_djbooths:client:pause", -1, boothId)

-- Late joiner requests current state:
Client → TriggerServerEvent("ds_djbooths:server:requestSync")
Server → TriggerClientEvent("ds_djbooths:client:sync", src, boothId, state)
Server → TriggerClientEvent("ds_djbooths:client:history", src, boothId, history)

Performance Notes

ConcernAnswer
History payload size~3 KB per booth at 30 entries (URL strings + timestamps). Negligible.
Broadcast frequencyHistory is only sent when a new track is queued or a player joins. Not polled.
Prompt mode CPUThe proximity poll runs every frame while a player is near a booth, and every 300 ms otherwise.
xsound per playerEach client manages its own xsound instance. The server stores state, not audio.

10 — FAQ

Can I use YouTube links?

Yes. DS DJ Booths uses xsound under the hood, which supports YouTube URLs via its embedded Chromium player. Paste the full YouTube URL (https://youtube.com/watch?v=… or https://youtu.be/…) into the URL input and press Enter or the arrow button.

YouTube's embedded player has a known memory leak in FiveM's Chromium (141+) caused by YouTube's new animated UI. xsound isolates each YouTube video in its own DUI and auto-recovers if it crashes. This is a YouTube / FiveM Chromium issue, not a ds_djbooths issue.

What audio formats are supported?

Any format xsound supports: YouTube URLs, direct .mp3 links, direct .ogg links, and SoundCloud links. Direct links must be publicly accessible (no auth headers).

Will everyone hear the music?

Yes. When a DJ queues a track, the server broadcasts the URL to every connected client. Each client starts its own xsound instance at the booth's 3D world position. Players within range hear it; players far away do not. Everyone within range hears the same track simultaneously.

What happens when a player joins mid-track?

On resource start the client fires ds_djbooths:server:requestSync. The server replies with the current playback state for every active booth (URL, volume, timestamp). The new player immediately begins playing the correct track at the correct seek position.

I changed my job but the booth option didn't update.

DS DJ Booths listens to QBCore:Client:OnPlayerUpdated to keep a local job cache fresh. Job changes take effect on the very next interaction check — no relog required. If you are experiencing issues, confirm your framework is firing this event correctly on job change.

Does history persist across server restarts?

No. History is stored in server memory only and resets when the resource or server restarts. If persistent history is needed, a SQL-backed extension would be required.

Can I mix target mode and prompt mode per booth?

Not currently. Config.TargetSystem is a global setting that applies to all booths. All booths use the same interaction system.
