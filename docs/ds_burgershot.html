DS Burgershot

Full-featured player-owned restaurant job. Employees cook real food through a multi-station kitchen pipeline, stock a live retail shop, bill customers at the cash register, manage staff via an in-game HR panel, and run deliveries for bonus pay — all inside a modular multi-framework, multi-inventory bridge system.

QBCore Qbox FiveM Lua 5.4 ox_inventory / qs-inventory / qb-inventory ox_lib oxmysql Escrow

1 — Overview

DS Burgershot is a complete player-run restaurant resource built around a realistic kitchen workflow. Employees collect raw ingredients, prep them at dedicated stations, cook proteins on the grill or deep fryer, and assemble finished burgers and sides before stocking them into the retail store for customers to purchase. A cash register billing system, in-game HR management, and a delivery mini-job round out the experience for every play style.

Feature summary

  • Five cooking stations — Cutting Board, BBQ/Grill, Deep Fryer, Assembly, and Drinks — each with its own target zone, animation, duration, and optional skill check
  • Multi-step cooking pipeline — raw ingredients → prepped → cooked → assembled finished item
  • Shared prep storage — intermediate items can be deposited and withdrawn by any on-duty employee
  • Live retail store — employees stock items; customers browse, add to cart, and checkout via the NUI shop
  • Boss-adjustable item prices — managers change store prices in-game without editing config
  • Cash register billing — employees generate a receipt item on every customer transaction
  • In-game HR panel — grade 3+ managers can hire, fire, promote, demote, and view the business bank balance
  • Duty clock-in/out zone — server-managed duty state with Discord webhook logging
  • Wardrobe ped — employees equip the restaurant uniform from a nearby NPC
  • Delivery mini-job — drive a van to randomised delivery locations for a pay bonus; items are consumed from inventory on delivery
  • Multi-framework bridge — QBCore and Qbox (ESX switchable via Config.Framework)
  • Auto-detecting inventory — supports ox_inventory, qs-inventory, ps-inventory, tgiann-inventory, and QBCore native
  • Multi-target bridge — ox_target, qb-target, or ds_target selectable via Config.Target
  • Discord webhook logs for all HR events, billing, and deliveries
  • Map blip and configurable optional world markers at all interaction zones

3 — Installation

  1. Place ds_burgershot inside your server's resources directory.
  2. Run or import SQL + items + job/setup.sql into your database — or let the resource auto-create the tables on first start.
  3. Add all item definitions from SQL + items + job/items.txt to your inventory resource (qb-inventory or ox_inventory format — both are included in the file).
  4. Add the job definition from SQL + items + job/job.txt to your framework's job list (qb-core/shared/jobs.lua for QBCore, or your ESX jobs table).
  5. Open shared/config.lua and set Config.Framework, Config.Inventory, Config.Target, and Config.Appearance to match your server.
  6. Adjust all location vectors in Config.Locations to fit your Burgershot interior.
  7. Add ensure ds_burgershot to server.cfg after all dependencies.
# server.cfg — ensure in this order
ensure oxmysql
ensure ox_lib
ensure qb-core          # or qbx_core

# DS Customs utilities (required)
ensure ds_notify
ensure ds_progressbar
ensure ds_prompt
ensure ds_businessbanking

# Your chosen target & inventory (examples)
ensure ox_target
ensure ox_inventory

ensure ds_burgershot
The SQL tables are created automatically on first server start using CREATE TABLE IF NOT EXISTS. The setup.sql file is provided for reference or manual import if preferred.

6 — Cooking Stations

Cooking stations are defined in Config.CookingStations. Each entry describes a physical target zone in the world, the ox_lib context menu items available at that station, and the recipe required to produce each output item.

Station schema

Config.CookingStations = {
    {
        id         = "cutting",          -- unique station identifier
        label      = "Cutting Board",
        menuId     = "cuttingBoard",     -- ox_lib context menu ID
        anim       = { dict = "...", clip = "..." },  -- animation played during cooking
        duration   = 10000,              -- milliseconds the progress bar runs
        skillCheck = true,               -- whether an ox_lib skill check fires mid-progress
        target     = {
            coords  = vector3(x, y, z),
            width   = 1.0, length = 3.2, heading = 35,
            minZ    = 10.97, maxZ = 13.97,
            icon    = "fa-solid fa-knife", label = "Cutting Board"
        },
        items = {
            { label = "Slice Potato", output = "cutpotato", recipe = {{ name = "potato", amount = 1 }} },
        }
    },
}

Default stations

StationProducesSkill Check

Stations that have skillCheck = true trigger an ox_lib skill-check challenge mid-progress. Failing cancels the current cook and refunds no ingredients.

8 — Store & Shop System

Employee Stocking

On-duty employees open the stock management NUI at the employeeStore target zone. From here they can deposit items from their inventory into the store, adjust prices (grade 3+ only), and view current stock levels. Items must be stocked before they appear in the customer shop.

Customer Shop

Any player can approach the customerStore target zone to open the shop NUI. Items are grouped by category (Burgers, Sides, Drinks) and show live stock counts and prices pulled from the database. Customers add items to a cart and pay in one checkout transaction. Payment is deducted from the player's bank account and deposited directly into the restaurant's ds_businessbanking account.

Cash Register Billing

Employees can also bill a nearby player directly from the CashRegister target zone. On a successful transaction, the customer's account is charged, the employee receives Config.BillingEmployeeCut × the transaction total as cash, and a bs_receipt item is given to the customer (if Config.ReceiptEnabled = true).

9 — HR System

The HR panel is accessible at the HRMenu target zone by any employee with grade ≥ 3. It provides full staff management without needing admin access or a server restart.

HR actions

ActionMin. GradeDescription
Hire3Set a player's job to burgershot at grade 0 (Trainee).
Fire3Remove a player from the burgershot job.
Promote3Increase a current employee's grade by 1.
Demote3Decrease a current employee's grade by 1.
View Business Bank3View the restaurant's current ds_businessbanking account balance.

All HR actions are logged to Discord via the configured webhook. Grade 4 (Owner) has no restriction on who they can promote or demote up to grade 3.

10 — Delivery System

On-duty employees can interact with the delivery NPC ped (Config.Locations.DeliveryPed) to start a delivery run. A delivery van spawns at Config.Locations.DeliveryVehicleSpawn and a random drop-off location from Config.DeliveryLocations is chosen as the waypoint.

On arrival at the drop-off point, the driver interacts with a customer ped model from Config.DeliveryTargetPedModels. The delivery items listed in Config.DeliveryItems are removed from the driver's inventory and a payout between Config.DeliveryMoney.min and Config.DeliveryMoney.max is deposited to their bank account.

Delivery items are taken from the employee's personal inventory, not the store stock. Employees must cook and hold items before starting a delivery run. Default delivery payout is $500–$1,000 per run.

11 — Job Definition

The default job grades are defined in SQL + items + job/job.txt. Paste the block into your framework's jobs file or database.

burgershot = {
    label = 'Burgershot Restaurant',
    type  = 'restaurant',
    defaultDuty = true,
    offDutyPay  = false,
    grades = {
        ['0'] = { name = 'Trainee',    payment = 80  },
        ['1'] = { name = 'Crew Member', payment = 120 },
        ['2'] = { name = 'Shift Lead',  payment = 170 },
        ['3'] = { name = 'Manager',     payment = 240 },
        ['4'] = { name = 'Owner',       isboss = true, payment = 350 },
    },
},

Grade 3 (Manager) is the minimum for HR access and price management. Grade 4 (Owner) has full boss privileges including viewing and managing the business bank account.

12 — Database Tables

Two tables are created automatically on first resource start using CREATE TABLE IF NOT EXISTS. No manual SQL import is required, but the file is provided in SQL + items + job/setup.sql for reference.

TablePurpose
ds_burgershot_store_inventoryPersists item stock levels and manager-set prices. One row per item. Seeded from Config.Store.AllowedItems on first start using INSERT IGNORE.
ds_burgershot_receiptsPurchase history — one row per billing transaction. Stores citizenid, item JSON, total, payment method (cash/bank), source type, and Unix timestamp.

15 — Notes & FAQ

  • Database tables are created automatically on first resource start using CREATE TABLE IF NOT EXISTS — no manual SQL import is required unless preferred.
  • Item definitions in items.txt must be added to your inventory resource before starting the server. Both qb-inventory and ox_inventory formats are provided in the same file.
  • Store item prices are seeded from Config.Store.AllowedItems on first start only (INSERT IGNORE). After that, changes to default prices in config have no effect — use the in-game employee stock NUI to update prices.
  • Employees must wash their hands at the WashingHands interaction point before any cooking station will allow them to cook. The state resets on duty-off.
  • Prep storage is shared between all on-duty employees — any employee can deposit prepped ingredients for another to use in assembly.
  • Config.BillingEmployeeCut controls only the cash payout to the billing employee. The full transaction amount is deposited to the business bank account regardless.
  • Set Config.Debug = true and check the server console for detailed logs if any station or zone is not triggering correctly after repositioning vectors.
  • The delivery NPC ped and wardrobe ped are spawned and managed server-side — their models are set via Config.DeliveryPedModel and Config.WardrobePedModel respectively.
  • If you change Config.JobName after first use, update the job definition in your framework accordingly and ensure the database has been cleared or migrated.
