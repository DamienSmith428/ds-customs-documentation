DS Mining

Multi-framework, multi-inventory, target-aware mining script with 11 ore types, a server-side refinery queue with progressive per-unit collection, an ox_lib skill check system on the refinery, a sell shop, pickaxe break mechanics, and a full NUI — by DS Customs

v1.0.0 QBX Core QB-Core ESX ox_inventory qb-inventory ps-inventory qs-inventory tgiann-inventory ox_lib oxmysql Lua 5.4 Escrow

1 — Overview

DS Mining is a complete ore mining economy for FiveM servers. Players head to any of the configurable rock nodes, equip a pickaxe, and mine raw ores via an animated progress bar. Mined ores can be sold directly at the sell shop NPC or submitted to the refinery NPC for server-side processing into refined bars and gems worth significantly more per unit.

All compatibility logic lives in isolated bridge files inside core/ — only the files matching your config are ever active. config.lua and strings.lua are fully open; all other files are escrow-protected.

3 — Installation

Drop-in

Copy the ds_mining folder into your resources directory.

Database — Fresh Install

Import the refinery queue table by running the included SQL file against your database:

-- sql/ds_mining_refining.sql
CREATE TABLE IF NOT EXISTS `ds_mining_refining` (
    `id`                  INT UNSIGNED   NOT NULL AUTO_INCREMENT,
    `citizenid`           VARCHAR(50)    NOT NULL,
    `input_item`          VARCHAR(60)    NOT NULL,
    `input_quantity`      INT UNSIGNED   NOT NULL DEFAULT 1,
    `output_item`         VARCHAR(60)    NOT NULL,
    `output_quantity`     INT UNSIGNED   NOT NULL DEFAULT 1,
    `started_at`          BIGINT         NOT NULL,
    `ready_at`            BIGINT         NOT NULL,
    `collected_quantity`  INT UNSIGNED   NOT NULL DEFAULT 0,
    PRIMARY KEY (`id`),
    INDEX `idx_citizenid` (`citizenid`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
Rows are hard-deleted once all units have been collected, so the table stays small over time. No periodic cleanup is needed.

Database — Upgrading from a Previous Version

If you already have the ds_mining_refining table from a prior install, run the migration file instead of the full schema — it adds only the two new columns and will not affect existing rows:

-- sql/migration.sql  (safe to run multiple times)
ALTER TABLE `ds_mining_refining`
    ADD COLUMN IF NOT EXISTS `started_at` BIGINT NOT NULL DEFAULT 0
    AFTER `output_quantity`;

UPDATE `ds_mining_refining` SET `started_at` = `ready_at` WHERE `started_at` = 0;

ALTER TABLE `ds_mining_refining`
    ADD COLUMN IF NOT EXISTS `collected_quantity` INT UNSIGNED NOT NULL DEFAULT 0
    AFTER `ready_at`;
Existing in-progress rows backfilled by the migration will have started_at = ready_at, which means they will appear as fully ready immediately when the player next opens the refinery. This is a one-time safe fallback — new jobs written after the migration will track correctly.

Inventory Items

Add all mining items to your inventory's item definitions. The ready-to-use definitions are in Install/items.txt (ox_inventory / QBCore / QBX format). For ESX servers, run sql/mining_items-ESX-ONLY.sql instead.

Copy the inventory images from Install/ into your inventory's images folder. Images are provided for all 11 raw ores, all 11 refined items, and the pickaxe.

server.cfg Start Order

ensure oxmysql
ensure ox_lib
ensure qbx_core      # or qb-core / esx
ensure ox_inventory  # or whichever inventory you use
ensure ox_target     # only if Config.UseTarget = true
ensure ds_mining

Quick-Start Config

Open configuration/config.lua and set the four keys to match your server stack:

Config.Framework      = 'qbx'         -- 'qbx' | 'qbcore' | 'esx'
Config.Inventory      = 'ox_inventory' -- 'ox_inventory' | 'qb-inventory' | 'ps-inventory' | 'qs-inventory' | 'tgiann-inventory'
Config.UseTarget      = true           -- true = target resource | false = E-prompt
Config.TargetResource = 'ox_target'   -- 'ox_target' | 'qb-target' | 'ds_target' (only used when UseTarget = true)
Players must obtain a pickaxe_mining item before they can mine. Add it to a shop or give it via an admin command — it is not handed out by default.

Refinery Skill Check — Config.refinerySkillCheck

When enabled, an ox_lib skill check fires on the client before the refinery submission event reaches the server. Keys 1–4 are used as inputs. If the check is passed the job is queued normally; if failed the configured penalty is applied.

KeyDefaultDescription
enabledtrueMaster toggle. false skips the skill check entirely for all ores, regardless of per-recipe skillCheck values.
loseOreOnFailfalsefalse — ore is fully returned on failure; player retries freely. true — a percentage of the submitted batch is forfeited (see losePercent).
losePercent50Percentage of the submitted quantity to remove on failure (1–100). Rounded down to the nearest whole unit; minimum 1. Only used when loseOreOnFail = true.
The per-recipe skillCheck key sets individual difficulty. Set it to false on a specific recipe to exempt that ore from the check even when the global enabled flag is true. The custom difficulty form accepts a table: { areaSize = 30, speedMultiplier = 1.5 } — refer to the ox_lib skill check docs for valid ranges.
Config.refinerySkillCheck = {
    enabled       = true,
    loseOreOnFail = false,  -- true = forfeit losePercent% of submitted ore on failure
    losePercent   = 50,     -- only used when loseOreOnFail = true
}

Notifications

Notifications are fired via the ds_customs:notify net event, which calls lib.notify by default. To swap the notification system, edit the RegisterNetEvent handler at the bottom of config.lua:

RegisterNetEvent('ds_customs:notify')
AddEventHandler('ds_customs:notify', function(title, message, msgType)
    lib.notify({
        title       = title,
        description = message,
        type        = msgType or 'inform',
    })
end)

Replace the body with any notification library your server uses. All notification strings are editable in configuration/strings.lua.

6 — Mining Flow

The full sequence from approach to ore in inventory:

StepWhereWhat happens
1 — InteractionClientPlayer enters a rock node (2 m radius). In E-prompt mode a text UI appears; in target mode a target option appears. Pressing E / selecting the option calls startMining(areaIndex).
2 — Pickaxe checkServer (callback)ds_customs:checkPick verifies the player has at least 1 pickaxe_mining in their inventory. If not, an error notification fires and mining is aborted.
3 — Rock dataServer (callback)ds_customs:getRockData picks a random entry from Config.rocks and returns its item name and mineTime to the client.
4 — Progress barClientThe pickaxe prop is attached to the player's right hand. The looping hammer animation plays. lib.progressBar runs for mineTime ms. Movement, vehicle entry, and combat are disabled. Player can cancel with the configured cancel key.
5 — Mine rockClient → ServerOn bar completion, the client fires ds_customs:mineRock. The server validates the player is within 10 m of the area, checks carry capacity, and awards the ore item.
6 — Axe break checkClient → ServerAfter a successful mine, the client rolls math.random(1, 100) < breakChance. If triggered, ds_customs:axeBroke removes the pickaxe_mining item server-side.

7 — Refinery Flow

The sequence from raw ore to refined item:

StepWhereWhat happens
1 — Open refineryClient → Server (callback)Player interacts with the refinery NPC. ds_customs:getRefineryData fetches all recipe definitions with the player's current ore counts, plus any pending/partially-collected queue rows. For each queue row it calculates collectableNow (units done minus already collected) and secondsToNext.
2 — Skill checkClientAfter the player confirms a quantity in the modal, lib.skillCheck fires (if Config.refinerySkillCheck.enabled = true and the recipe has a difficulty set). Keys 1–4 are used as inputs. On failure: if loseOreOnFail = false the ore is returned and the player retries; if loseOreOnFail = true the server event ds_customs:forfeitOre removes losePercent% of the submitted quantity.
3 — Submit jobClient → Server (event)On skill check pass (or if check is disabled), ds_customs:startRefining validates proximity (<5 m), available ore count, deducts the input ores, and inserts a row with started_at = os.time() and ready_at = started_at + (refineTime × quantity).
4 — Timer (per unit)Server (database) + Client (UI)No active server thread runs. The server derives units_done = floor((now − started_at) / refineTime) on demand. The queue UI in the NUI ticks a live countdown to the next unit and updates the "X / Y ready" counter in real time.
5 — Collect (partial or full)Client → Server (event)Player clicks Collect. ds_customs:collectRefined derives collectable = units_done − collected_quantity. If > 0: items are awarded, collected_quantity is updated (or the row deleted when all units are collected). If 0: "Not Ready" notification fires.
If the player's inventory is full at collection time, the row and its collected_quantity counter are unchanged — they can try again after freeing space. Refined items are never lost.

8 — Database Schema

ds_mining_refining (
    id                  INT UNSIGNED   AUTO_INCREMENT PRIMARY KEY,
    citizenid           VARCHAR(50)    -- player identifier from the active framework
    input_item          VARCHAR(60)    -- raw ore item name (e.g. 'iron_mining')
    input_quantity      INT UNSIGNED   -- how many units were submitted
    output_item         VARCHAR(60)    -- refined item name (e.g. 'iron_refined')
    output_quantity     INT UNSIGNED   -- total units to be produced (= input_quantity)
    started_at          BIGINT         -- Unix timestamp when the job was submitted
    ready_at            BIGINT         -- Unix timestamp when ALL units are done
    collected_quantity  INT UNSIGNED   -- units the player has already collected (partial collection)
    INDEX idx_citizenid (citizenid)
)
Per-unit readiness is derived on demand: units_done = floor((now − started_at) / refineTime). The refineTime per unit is back-calculated as floor((ready_at − started_at) / output_quantity) — no extra column needed.

Rows are hard-deleted when collected_quantity = output_quantity. To manually clear a stuck job: DELETE FROM ds_mining_refining WHERE id = <id>;

12 — FAQ

Players can't start mining — "No Pickaxe" every time.

The server callback ds_customs:checkPick checks for the item pickaxe_mining (note the _mining suffix — not plain pickaxe). Confirm the item name in your inventory definitions matches exactly. Also verify the item was added to Install/items.txt (or the ESX SQL file) and that your inventory resource was restarted after the import.

Rock nodes aren't showing interaction prompts.

Verify Config.UseTarget and Config.TargetResource match your running setup. If using ox_target, confirm it starts before ds_mining. In E-prompt mode (UseTarget = false), the prompt only appears within 2 m of a rock node — stand closer. Check the F8 console for any bridge load errors on startup.

Players are getting kicked when their axe breaks.

The ds_customs:axeBroke server event removes pickaxe_mining from the player's inventory. If the item is not found when the event fires, the player is kicked as a potential exploit. This can happen if the item was removed by another script between the client-side check and the server event arriving. Ensure no other resource is consuming the pickaxe item concurrently. You can adjust the anti-cheat tolerance by editing the axeBroke handler in the escrow-protected server file.

The skill check fires but nothing happens after it.

The NUI focus is released before lib.skillCheck runs so the overlay can capture key input. If the check appears to silently fail, confirm ox_lib is running and that the per-recipe skillCheck value is a valid string ('easy', 'medium', 'hard') or a correctly-formed table. Setting it to false disables the check for that recipe only.

Player lost ore on a skill check fail but shouldn't have.

Verify Config.refinerySkillCheck.loseOreOnFail is set to false. When false, the server event is never fired on failure and no ore is removed. The notification strings for the two failure modes (skillcheck_failed_safe vs skillcheck_failed) are separate — confirm the correct one is showing to rule out a notification display issue.

Refinery job is stuck — player can't collect.

Connect to your database and check the ds_mining_refining table for the player's citizenid. Confirm that started_at is populated (non-zero) — rows migrated from a previous version that lack a real started_at will have it set to ready_at, which means they will show as fully ready. If collection still fails despite the timestamps looking correct, confirm the player is within 5 m of the refinery ped and that Config.refineryShop.coords matches the actual ped position. To manually clear a stuck row: DELETE FROM ds_mining_refining WHERE id = <id>;.

Player collected some units but the row is still in the queue.

This is expected behaviour. The row persists until collected_quantity = output_quantity (all units collected). The player can open the refinery again to collect more units as they finish. The Collect button shows the exact count available and is disabled while zero are ready.

Getting a canCarryItem error on ESX.

Set Config.oldESX = true in config.lua. This switches the carry check to the legacy ESX weight/limit API instead of the modern canCarryItem export.

Can I add more ore types?

Yes. Add an entry to Config.rocks with the item name, price range, mine time, and image filename. If you want it refinable, add a matching entry to Config.refinedrocks. Create the item definition in your inventory and add the item images to html/images/. The server and NUI read all entries at startup — no core code changes are required.

How are sell prices calculated?

Each ore item sold calls math.random(price[1], price[2]) once per unit. The total reward is the sum of all individual rolls. This means selling 10× iron ore at {70, 100} will award between $700 and $1,000, distributed randomly per item.

How do I change the notification system?

Edit the ds_customs:notify event handler at the bottom of configuration/config.lua. Replace lib.notify with your preferred notification library. The handler receives title, message, and msgType ('success', 'error', 'inform') as arguments.
